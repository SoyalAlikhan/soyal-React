Section 09Live Classes + Auto Attendance Engine

Aapki Core Requirement

9.1 Class Scheduling

Teacher live class banata hai in fields ke saath:

  • Course + Batch select (batch ke sab enrolled students auto-invite)
  • Title, Date, Start Time, Duration (yeh attendance calculation ka base hai)
  • Recurring option — "Daily", "Mon-Fri", "Weekly", ya custom days
  • Recurring class ki end date = course ki duration tak automatic (aapki requirement ke mutabiq)
  • Recording on/off, Chat on/off, Waiting room on/off
  • Attendance threshold % (default 75%, teacher change kar sakta hai)

System pura series generate kar deta hai — agar course 3 mahine ka hai aur daily class hai, toh ~90 class instances ban jaate hain aur sab calendar mein dikhte hain.

9.2 Attendance Kaise Calculate Hogi

Yeh pura automatic hai — teacher ko kuch mark nahi karna. Video SDK ke join/leave events se hota hai:

  1. Student "Join" dabata hai → backend joinTime record karta hai (ek naya session object)
  2. Student nikalta hai (ya net chala gaya) → leaveTime record hota hai, us session ka duration calculate hota hai
  3. Wapas aaya? → naya session object add hota hai. Ek student ke multiple sessions ho sakte hain
  4. Class khatam → sab sessions ka totalDuration sum hota hai
  5. attendancePercentage = totalDuration / classDuration × 100
  6. Status auto-set: Present (≥75%), Partial (30–74%), Absent (<30%)
Edge cases jo handle karne hain:
  • Browser crash / tab band: SDK ka disconnect webhook aayega — leaveTime set ho jayega. Agar webhook na aaye toh class end par pending sessions ko auto-close karo (leaveTime = classEndTime ya lastHeartbeat).
  • Heartbeat: Har 30 second client ek ping bheje. 90 sec tak ping na aaye = disconnected maano.
  • Late join: Agar student 40 min ki class mein 35 min baad aaya — duration kam hoga, auto Absent. Teacher manual override kar sakta hai (reason ke saath, audit log mein save).
  • Teacher late/absent: Agar teacher join hi nahi hua, class "Not Conducted" mark ho — kisi student ki attendance affect na ho.
  • Frequent disconnects: Agar 5+ sessions hain toh flag "Network Unstable" — teacher ko dikhe ke ye jaan-bujh kar nahi gaya tha.
  • Multi-device: Ek student ka ek hi active session — dusre device se join kare toh pehla disconnect ho.

17A.4 Technical Requirements

  • i18n library: next-intl ya i18next — har string JSON locale file mein (/locales/ur.json, /locales/hi.json…). Code mein koi hardcoded text na ho.
  • URL structure: /ur/courses/tajweed, /hi/courses/tajweed — SEO ke liye har language ka apna URL, aur hreflang tags lagein.
  • RTL support: Urdu/Arabic ke liye dir="rtl", CSS logical properties use karein (margin-inline-start na ke margin-left) — warna layout ulta ho jayega.
  • Fonts: Noto Nastaliq Urdu (Urdu), Amiri / KFGQPC Uthmanic (Quranic text), Noto Sans Devanagari/Bengali/Tamil/Telugu/Malayalam. Font subsetting karein warna page bhari ho jayega.
  • Quranic text hamesha Arabic mein hi rahega — sirf tarjuma aur tafseer translate honge. Ye rule system mein enforce ho.
  • Numbers & dates: Arabic-Indic numerals option (١٢٣) + Hijri calendar support ke saath Gregorian.
  • Video subtitles: Har lesson video ke saath multiple .vtt subtitle files attach ho sakein.
  • Search: Har language ka apna text-search index; Arabic mein diacritics ignore karna.

17A.5 Content Translation Policy

Bohat zaroori rule: Religious content machine translation se kabhi publish na ho. Google Translate "Sunnah" ka tarjuma kuch bhi kar sakta hai. Har translation scholar review se guzre — ya kam az kam ek native speaker Islamic reviewer se.
  • Teacher apna course ek primary language mein banaye
  • Translation ek alag workflow ho: Translator → Reviewer → Publish (content review jaisa hi)
  • AI se draft translation ban sakti hai (time bachane ke liye), lekin human review ke bina publish nahi
  • Open-source community translation: Weblate/Crowdin jaisa setup — volunteers UI translate karein, maintainer approve kare. Ye aapke open-source model ke saath perfect fit hai.
  • Har translation par credit: "Translated by ___, Reviewed by ___"

19A.4 Ek Bohat Zaroori Warning — App Store Commission

Google Play aur Apple App Store digital course ki sale par 15–30% commission lete hain agar payment app ke andar ho. Aapka platform khud 15% le raha hai — agar upar se Apple 30% le le, toh teacher ke paas kuch nahi bachega.

19A.4A Ye Commission Lagta Kyun Hai — Aur Bachne Ka Tareeqa

Naya — Clarification

Sawaal uthta hai: database, server, app — sab kuch apna hai, toh Google/Apple beech mein commission kyun le rahe hain? Wajah simple hai — woh backend ka nahi, apne Distribution Store (App Store/Play Store) ka commission lete hain.

  • Distribution channel unka hai: iPhone/Android user sirf unke store se app install kar sakta hai. List hona hai toh unke rules maanne padenge.
  • In-App Purchase (IAP) rule: Agar koi digital content/service (course, subscription) app ke andar khareeda jaata hai, toh transaction unke apne payment system (Apple IAP / Google Play Billing) se guzarna mandatory hai — Razorpay/Stripe seedha app ke andar allowed nahi. Unka payment system use karne ka matlab unka 15–30% commission automatic kat jaata hai.
  • Rule sirf digital goods par hai, physical par nahi: Isiliye Uber/Zomato/Amazon commission nahi dete (physical delivery hai), lekin Netflix/Spotify/Udemy jaisi digital content company ko dena padta hai.

Netflix/Spotify jaisa "Reader App" tareeqa — bachne ka solution

Apple ne 2022 mein kuch categories (video, music, magazines, aur education/EdTech bhi) ko chhoot di thi — woh account/purchase external website par manage karne ka mention kar sakti hain, bas app ke andar seedha "Buy" button ya external payment link nahi de sakti.

Strategy — Commission se bachne ka plan
  • Website/PWA par koi restriction nahi — seedha Razorpay Route use karo, apna 100% control, koi third-party cut nahi. Isiliye pehle website se shuru karna sahi decision hai.
  • Native app sirf "consumption" ke liye banayein — jo already khareeda hua hai wahi dekhna, live class, homework, attendance. Purchase flow app mein bilkul na rakhein.
  • Paid enrollment ka checkout hamesha website/browser mein ho — app se "Continue on website" par tap kare, browser khule, wahan pay kare, wapas app mein aaye.
  • Free courses, live classes, aur pehle se enroll kiye hue paid courses — sab app ke andar bina kisi restriction ke chalte rahenge.
  • Architecture din-1 se aisi banayein ke payment logic app se independent ho (sirf website/API se trigger ho) — taaki baad mein app store rejection ka risk na aaye.

19A.5 App Store Approval ke liye dhyan rakhne wali baatein

  • User-generated content hai (koi bhi course bana sakta hai) — Apple ko report/block mechanism chahiye. Achhi baat ye hai ke Section 15 mein wo already hai.
  • Kids ke liye app — agar 13 se kam age ke users hain toh "Kids Category" ke strict rules apply honge (no ads, no external links, parental gate)
  • Account deletion app ke andar se possible hona chahiye (Apple mandatory requirement)
  • Privacy policy aur data usage disclosure — dono stores par mandatory
  • Religious content par dono stores generally theek hain, lekin content policy page rakhna zaroori hai
